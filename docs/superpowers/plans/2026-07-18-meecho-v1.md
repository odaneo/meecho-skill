# Meecho V1 全局声音档案 Plugin 实施计划

> **供执行计划的智能体使用：** 实施时使用 `superpowers:executing-plans`，逐任务执行；用户要求直接在 `main` 上工作，不创建分支或 worktree。每完成一个任务，先给用户展示容易理解的结果，再等待下一步指示。

**目标：** 做一个可从 GitHub 安装的 Meecho Plugin。它包含一个显式调用的 `meecho` Skill，能够把用户本地旧作整理成全局私人声音档案，并在任何项目中按该档案写作或润色。

**架构：** Plugin 只保存通用工作流，不保存私人文章。私人声音档案位于当前 Windows 用户的 `%USERPROFILE%\.meecho\`。日常写作和润色只在聊天中返回文字；只有用户明确要求建立、更新、记住偏好、导出或删除时才写本地文件。

**技术栈：** Codex Plugin、Codex Skill、Markdown、YAML、JSON、JSONL、Git、GitHub Actions。PowerShell 和 Python／`python-docx` 只在开发、测试和 Word 导入时使用，不进入最终 Plugin。

## 全局约束

- 最终产品是一个 Meecho Plugin，内部只包含一个 `meecho` Skill。
- 用户安装 Plugin，不需要手工复制或另外安装 Skill。
- Skill 的规范调用名是 `$meecho:meecho`。
- `allow_implicit_invocation` 必须为 `false`；没有显式调用时不得读取声音档案。
- 全局私人数据固定保存在 `%USERPROFILE%\.meecho\`。
- 私人原文、私人档案和私人评测结果不得进入 GitHub、Plugin 缓存或项目目录。
- 普通写作和润色只返回聊天文字，不创建 `drafts/`、`sessions/` 或项目文件。
- 只有明确的 `build`、`update`、`remember`、`export`、`delete` 请求可以写文件。
- 不训练、微调、继续预训练或修改任何模型权重。
- 不使用 LoRA、SFT、DPO、RLHF、prompt tuning、soft prompt、activation steering、作者分类器或个性化参数拟合。
- 最终 Plugin 不包含 Python、Node.js、数据库、向量库、MCP Server、Hook、App 或后台服务。
- 高中原文与成年博客保持原位、保持只读。
- 成年博客只用于区分时期变化，不自动当作负样本。
- 高可信风格结论至少需要两个独立作品族支持，并记录反例或适用边界。
- 封存作品不得参与档案编译或提示优化。
- 用户本人盲选是最终声音相似性的主要评价；自动评分只作辅助。
- 真实私人语料只在任务 9 接入；任务 1–8 只使用合成语料。
- 用户的 `.doc`／`.docx` 文件在任务 9 前提供；开发工具读取副本，不覆盖原件。
- 测试日志全部保存在本地 `evals/logs/`，默认不提交 GitHub。
- 不创建第二个 Windows 用户，不创建独立 `CODEX_HOME`，不伪造 `HOME`／`USERPROFILE`，不再使用重型评测测试舱。
- 开发评测使用当前 Codex 正常登录环境。写作基线使用只读 sandbox；运行前后检查项目状态。
- 同一轮前后对比必须记录模型、reasoning、提示词和输入文件版本。无法保证相同时，结果必须注明“仅供参考”，不得称为严格对照实验。

## 二、普通用户流程

1. 从 GitHub marketplace 安装 Meecho Plugin。
2. 第一次运行 `$meecho:meecho build`，选择本地旧作和成年博客。
3. 审阅生成的声音档案；确认后保存到 `%USERPROFILE%\.meecho\`。
4. 在任意项目显式调用 `$meecho:meecho` 写作或润色。
5. 需要调整时显式运行 `update` 或 `remember`。
6. Plugin 更新或卸载不删除私人档案。

## 四、实施任务

### 任务 1：记录没有 Meecho 时的普通写作基线

#### 这项任务到底做什么

任务 1 只回答一个问题：

> 在 Meecho 尚未安装、没有声音档案时，普通 Codex 面对固定写作题会写成什么样？

它不是安全测试，不是 Plugin 测试，也不是 Windows 隔离实验。它不要求结果一定失败；它只忠实记录现状，供任务 7 做前后对比。

#### 这项任务明确不做什么

- 不创建第二个 Windows 用户。
- 不修改或替换当前 `CODEX_HOME`。
- 不伪造 `HOME`、`USERPROFILE`、SQLite state 或认证文件。
- 不使用 `ProcessStartInfo` 直接启动 WindowsApps 内的可执行文件。
- 不建立 control／treatment 双舱。
- 不测试 allow／deny permission matrix。
- 不读取用户的高中作品或博客。
- 不安装或开发 Meecho Plugin。
- 不把“CLI 启动方式”本身当成研究成果。

#### 输入

- 仓库内完全虚构的高中作品族、成年对照文本和封存文本。
- 固定模型：`gpt-5.6-sol`。
- 固定 reasoning：`high`。
- 五个固定写作题。

#### 五个写作题

| 编号 | 用户能理解的测试目的 | 给 Codex 的材料 |
|---|---|---|
| 1 | 不给任何风格参考时，它自然会怎么写 | 只有场景要求 |
| 2 | 直接给三段旧作时，它能否临时模仿 | 三个合成高中作品族 |
| 3 | 它能否把一段普通文字润色成目标声音 | 待润色文字＋合成旧作 |
| 4 | 换到旧作没有写过的题材后，风格是否还在 | 合成旧作＋全新题材 |
| 5 | 两种叙述声音能否区分，并且不照抄鲜明句子 | 两种声音示例＋禁抄句 |

#### 评分方法

每题只看四项，每项 `0–2` 分，总分 `0–8`：

1. 是否完成用户要求。
2. 是否呈现目标句法、节奏和叙述距离。
3. 是否把“风格”迁移到新内容，而不是复制旧题材。
4. 是否避免逐字复用鲜明句子。

每题除分数外，只写一至两句中文判断。这里不使用复杂统计，不调用第二个模型充当裁判。

#### 用户最终看到的结果

`evals/results/baseline-summary.md` 必须采用下面的固定格式：

```markdown
# 任务 1：无 Meecho 写作基线

状态：完成
一句话结论：……
模型：gpt-5.6-sol
Reasoning：high
运行时间：……

| 题目 | 测试什么 | 分数 | 容易理解的结论 | 原始回答 |
|---|---|---:|---|---|
| 1 | 无参考自由写作 | 4/8 | …… | 本地日志链接 |
| 2 | 直接参考旧作 | 6/8 | …… | 本地日志链接 |
```

只有五题都产生真实回答和评分时，状态才能写“完成”。如果 Codex CLI 无法正常运行，摘要只能写：

```text
状态：未运行
原因：Codex CLI 无法启动
```

不得再使用需要用户猜测含义的内部状态词。

#### 本地日志

每次运行建立一个目录：

```text
evals/logs/<run-id>/
├── run.json
├── tests/
│   ├── result.json
│   ├── stdout.txt
│   └── stderr.txt
├── case-01/
│   ├── prompt.md
│   ├── response.md
│   ├── events.jsonl
│   ├── stderr.txt
│   └── score.json
├── case-02/
└── ...
```

- `run.json` 记录时间、Git commit、模型、reasoning 和每题退出码。
- `tests/` 保存 runner 测试的结论、标准输出和错误输出。
- `prompt.md`、`response.md` 和 `score.json` 让用户能直接检查测试。
- `events.jsonl`、`stderr.txt` 用于开发者排错。
- 整个 `evals/logs/<run-id>/` 只保存在本地，由 `.gitignore` 排除。
- GitHub 只提交不含原始对话的 `baseline-summary.md`。

- [ ] **步骤 3：先写一个最小 runner 测试**

`Test-BaselineRunner.ps1` 只验证：

1. 恰好发现五个 case。
2. `-DryRun` 能创建预期日志目录和五份 `prompt.md`。
3. 不会修改 `HOME`、`USERPROFILE` 或 `CODEX_HOME`。
4. `-RunRoot` 指向缺少 response 或 score 的目录时验证失败。
5. `-RunRoot` 指向五份 response 和 score 都存在的目录时验证通过。

运行命令：

```powershell
pwsh -NoProfile -File .\evals\tests\Test-BaselineRunner.ps1
```

预期：旧 runner 尚未简化时测试失败。

- [ ] **步骤 4：实现一个普通的基线 runner**

`Invoke-Baseline.ps1` 直接使用当前 shell 能找到的 `codex` 命令，不清洗环境、不复制认证文件、不自己启动 WindowsApps 二进制。

- `Invoke-Baseline.ps1 -DryRun`：只建立当次日志目录和五份最终提示词，不调用模型。
- `Invoke-Baseline.ps1`：顺序运行五题，打印本次 `RunRoot`。
- `Invoke-Task1Tests.ps1 -RunRoot <本次日志目录>`：运行结束后检查五题日志与评分是否完整。

每题等价运行：

```powershell
codex exec `
  --sandbox read-only `
  --model gpt-5.6-sol `
  -c 'model_reasoning_effort="high"' `
  --json `
  --output-last-message '<response.md>' `
  '<完整题目提示词>'
```

脚本把 stdout 保存为 `events.jsonl`、stderr 保存为 `stderr.txt`，并保留 `--output-last-message` 写出的最终回答。官方 Codex 手册说明 `codex exec` 默认使用只读 sandbox，`--json` 输出 JSONL，`--output-last-message` 可把最终消息另存为文件；这里仍显式写出 `--sandbox read-only`，让日志一眼可查。

脚本不得要求 API Key，不改变当前登录方式。单题失败时停止，把已经生成的日志保留下来，并在摘要写普通中文原因。

- [ ] **步骤 5：运行五题并评分**

运行：

```powershell
pwsh -NoProfile -File .\evals\scripts\Invoke-Task1Tests.ps1
pwsh -NoProfile -File .\evals\scripts\Invoke-Baseline.ps1
```

执行者直接阅读五份回答，按四项 rubric 评分，在每个 `score.json` 中写分数和一至两句说明，然后生成 `baseline-summary.md`。最后运行：

```powershell
pwsh -NoProfile -File .\evals\scripts\Invoke-Task1Tests.ps1 `
  -RunRoot '<Invoke-Baseline.ps1 打印的目录>'
```

- [ ] **步骤 6：向用户交付容易理解的结果**

完成时只汇报：

1. 五题是否全部跑完。
2. 每题分数和一句话结论。
3. 最明显的三个普通模型缺口。
4. 本地汇总和日志链接。
5. Git commit。

不得用测试框架内部名词代替结论。

#### 完成标准

- 五题都有真实 `prompt.md`、`response.md`、`events.jsonl`、`stderr.txt` 和 `score.json`。
- `Invoke-Task1Tests.ps1` 通过，并有自己的本地测试日志。
- `baseline-summary.md` 是普通中文表格，用户不读代码也能理解。
- 模型和 reasoning 明确记录。
- 运行前后没有预期之外的项目文件变化。
- 没有读取或修改 `%USERPROFILE%\.meecho\`。
- 没有安装 Meecho。

### 任务 5：定义从文章到声音档案的编译流程

**目的：** 不训练模型，只让大模型从本地语料中整理有证据的风格规律。

**流程：**

2. 识别不同叙述声音。
3. 提取句法、节奏、视角、注意力和情感距离。
4. 把题材词与真正风格分开。
5. 每条高可信规则寻找至少两个作品族证据。

7. 只选择少量短例句，不复制整篇文章。
8. 让用户审阅后再保存。

**完成标准：** 合成语料可以生成完整档案；封存文本和成年博客边界正确。

### 任务 6：定义写作、润色和管理行为

**目的：** 让声音档案真正影响聊天输出，同时保持普通操作只读。

**写作流程：**

1. 读取活动 profile。
2. 根据当前任务选择相关规则。
3. 选择 4–6 个跨作品族短例句。
4. 先保证内容正确，再应用声音特征。
5. 检查照抄、题材污染、过度成熟化和刻意仿古。
6. 在聊天中只返回一份正文。

**管理行为：**

- `status`：只读。
- `build`／`update`／`remember`：明确写入并接受 Codex 审批。
- `export`：导出副本，不改变源档案。
- `delete`：展示准确路径并再次确认。

**完成标准：** 合成 profile 可以用于写作和润色；普通请求不修改项目或档案。

### 任务 7：用同一组题对比 Meecho 前后

**目的：** 用普通人能看懂的方式证明 Meecho 是否真的改善了输出。

**轻量对比方法：**

- 使用任务 1 的同五题、同一模型、同一 reasoning。
- 在同一轮中先运行普通请求，再运行显式 `$meecho:meecho` 请求。
- 普通请求不得加载 Meecho；Meecho 请求读取合成声音档案。
- 不建立两个 `CODEX_HOME`，不建立虚拟 Windows 用户。
- 每组保存两份回答和一份并排评分。

**结果格式：**

```markdown
| 题目 | 普通 Codex | Meecho | 改善了吗 | 最明显差异 |
|---|---:|---:|---|---|
| 无参考写作 | 4/8 | 6/8 | 是 | 叙述距离更接近 |
```

**安全行为另做一张人工检查表：**

- [ ] 未显式调用时不读取档案。
- [ ] 普通写作只返回聊天文字。
- [ ] `status` 不写文件。
- [ ] 建立／更新时批准后才写入。
- [ ] 用户拒绝审批后没有部分文件。
- [ ] Plugin 更新后合成测试档案仍在。

这些检查使用合成档案。若真实 `%USERPROFILE%\.meecho\` 已存在，先停止，不覆盖用户数据。

**完成标准：** 五组前后回答、五组评分、并排汇总表和六项人工安全检查都存在。结果不使用“无限接近”等无法证明的表述。
