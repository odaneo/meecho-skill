# Meecho V1 全局声音档案 Plugin 实施计划

> **供执行计划的智能体使用：** 实施时使用 `superpowers:executing-plans`，逐任务执行；直接在 `main` 上工作，不创建分支或 worktree。每完成一个任务，向用户展示“做成了什么”，不要用内部测试术语代替结果。

**目标：** 构建一个可从 GitHub 安装的 Meecho Plugin。它包含一个显式调用的 `meecho` Skill，可以把用户选择的目标语料整理为全局私人声音档案，并在任何项目中按该档案写作或润色。

**架构：** Plugin 只保存通用工作流，不保存私人文章，也不附带 Meecho 自定义
运行时。Skill 由 Codex 执行：大模型负责逐篇分析和跨作品归纳，Codex 宿主
已有的文档能力读取用户选定的 `.docx`，文件工具经批准后写入档案。私人档案
位于当前 Windows 用户的 `%USERPROFILE%\.meecho\`。日常写作与润色只在聊天
中返回文字；只有用户明确要求建立、更新、记住偏好、导出或删除时才写文件。

**技术栈：** Codex Plugin、Codex Skill、Codex 宿主文档与文件工具、Markdown、
YAML、JSON、JSONL、PowerShell、Git、GitHub Actions。PowerShell 只用于仓库
开发、验证和安装调试，不进入最终 Plugin。

## 全局约束

- 最终产品是一个 Meecho Plugin，内部只包含一个 `meecho` Skill。
- 用户安装 Plugin，不需要手工复制或另外安装 Skill。
- 普通用户只需要 Codex 和 Meecho Plugin，不需要另外安装 Word、LibreOffice、
  Python、Java、Node.js 或 Meecho 本地服务。
- Skill 的规范调用名是 `$meecho:meecho`。
- `allow_implicit_invocation` 必须为 `false`；没有显式调用时不得读取声音档案。
- 全局私人数据固定保存在 `%USERPROFILE%\.meecho\`。
- 私人原文、私人档案和私人评估结果不得进入 GitHub、Plugin 缓存或项目目录。
- 普通写作和润色只返回聊天文字，不创建 `drafts/`、`sessions/` 或项目文件。
- 只有明确的 `build`、`update`、`remember`、`export`、`delete` 请求可以写文件。
- 不训练、微调、继续预训练、蒸馏或修改任何模型权重。
- 不使用 LoRA、SFT、DPO、RLHF、prompt tuning、soft prompt、activation steering、作者分类器或个性化参数拟合。
- 最终 Plugin 不包含 Python、Node.js、数据库、向量库、MCP Server、Hook、App 或后台服务。
- 目标语料和可选对照语料保持原位、保持只读。
- V1 的文件输入只支持有效、未加密的 `.docx`；不支持 `.doc`、`.docm`、
  `.dotx`、`.odt`、`.rtf`、PDF 或伪装扩展名。
- DOCX 正文由当前 Codex 宿主已有的文档能力读取。当前宿主无法读取时安全
  停止，不安装转换器或其他运行时。
- 对照语料可以完全不提供；提供时只用于区分表达差异，不自动当作负样本。
- 高可信风格结论至少需要两个独立目标作品族支持，并记录反例或适用边界。
- 封存作品不得参与档案编译、提示调整或例句选择。
- 真实私人语料只在任务 9 接入；任务 1–8 只使用合成语料。
- 用户的 `.docx` 文件在任务 9 前提供；Codex 宿主直接只读访问，不创建转换
  副本，不覆盖原件。
- “本地保存”只约束文件持久化位置，不代表离线推理。用户明确选择的 DOCX
  正文会进入 Codex 模型上下文；文档、档案和日志仍不得被 Meecho 复制到云端
  存储、GitHub、Plugin 缓存或项目目录。
- 测试日志保存在本地 `evals/logs/`，默认不提交 GitHub。
- 不创建第二个 Windows 用户，不创建独立 `CODEX_HOME`，不伪造 `HOME`／`USERPROFILE`。

### 唯一有效的风格判断规则

- Codex、其他模型、自动 rubric 和程序都无权判断“像不像目标风格”。
- 开发过程中禁止生成风格总分、相似度百分比、AI 胜率或“符合／部分符合／不符合”的主观结论。
- Codex 可以出最终测试题、生成匿名候选和记录用户选择，但不能替用户作出选择。
- “Meecho 是否真的更像”只在最后一个任务中评估，而且只以用户本人的盲选与明确结论为准。
- 用户没有完成最终盲选，项目不得宣称风格模仿已经有效。

### 开发测试与最终评估的区别

| 阶段 | 可以判断什么 | 不可以判断什么 |
|---|---|---|
| 开发测试 | Plugin 能否安装、Skill 是否只显式触发、文件是否写到正确位置、普通写作是否零写入、schema 是否有效、权限拒绝后是否停止 | 文字好不好、像不像目标风格、是否有某种主观感觉 |
| 最终评估 | 用户在匿名候选中选择哪份更像目标声音，或认为没有区别／都不像 | Codex 不得代替用户选择，也不得把自己的解释当成结论 |

凡是需要“读完一段文字后凭感觉判断”的检查，都不得出现在任务 1–9 的完成标准中。

## 二、普通用户流程

1. 从 GitHub marketplace 安装 Meecho Plugin。
2. 第一次运行 `$meecho:meecho build`，选择有效、未加密的 `.docx` 目标语料；
   如有需要，再选择 `.docx` 对照语料。
3. 审阅系统提取的风格证据，纠正事实错误后保存到 `%USERPROFILE%\.meecho\`。
4. 在任何项目显式调用 `$meecho:meecho` 写作或润色。
5. 完成开发后，由 Codex 出题并生成匿名候选。
6. 用户本人盲选哪份更像目标声音，或明确选择“没有区别／都不像”。

### 任务 4：定义从文章到证据型档案的流程

**创建：**

- `plugins/meecho/skills/meecho/references/build-profile.md`
- `evals/fixtures/build/basic/analysis-inputs.json`
- `evals/functional/Test-BuildBoundaries.ps1`

**流程：**

1. 只接受用户明确选择的有效、未加密 `.docx`，并由 Codex 宿主已有文档
   能力读取；不得安装或调用格式转换器。
2. 按完整作品划分开发集和封存集。
3. 区分目标语料、可选对照语料和封存语料。
4. 从句法、节奏、视角、注意力和情感距离提取候选规律。
5. 每条高可信规律至少寻找两个目标作品族的支持。
6. 保存反例、适用边界和不确定项。
7. 只选择少量短例句，不复制完整原文。
8. 向用户展示证据来源，让用户纠正事实错误。

任务 4 现有的 Markdown 合成语料只用于测试“宿主已经提供正文之后”的证据
归纳阶段，不代表 V1 接受 Markdown 用户文件。真实的 DOCX 宿主读取在任务 7
做端到端验证。

**客观测试只检查：**

- 封存文件没有出现在输入清单。
- 可选对照语料没有被标记为自动负样本。
- 完全不提供对照语料的输入清单仍然合法。
- 高可信规则至少引用两个目标作品族 ID。
- 私人原文没有被复制到 Plugin 或项目。
- 输出文件符合任务 3 的 schema。

**禁止：** Codex 不得评价档案“像用户”“有灵魂”或“达到多少相似度”。

**实施状态：** 已完成；合成输入、证据型合成档案和全部客观边界检查已通过。

### 任务 5：定义写作、润色和管理协议

**创建：**

- `plugins/meecho/skills/meecho/references/write-and-revise.md`
- `plugins/meecho/skills/meecho/references/privacy-and-permissions.md`
- `evals/functional/Test-WriteBoundaries.ps1`

**普通写作流程：**

1. 读取活动 profile。
2. 只选择与当前任务有关的规则和短例句。
3. 先满足内容要求，再应用档案中的表达约束。
4. 检查是否出现与本次可读取的私人原文或档案短例句完全相同、去除空白后
   不少于 20 个连续汉字的片段；命中时停止并重新生成。
5. 只在聊天中返回一份正文。

全局档案不保存原始文章路径和全文。用户没有为本次操作重新选择原文件时，
只能检查当前上下文与档案短例句，不得声称已经对全部历史原文完成逐字检查，
也不得自行扫描磁盘寻找旧语料。

**管理动作：**

- `status`：只读。
- `build`／`update`／`remember`：明确请求并接受 Codex 写入审批。
- `export`：导出副本，不改变源档案。
- `delete`：展示准确路径并再次确认。

**客观测试只检查：**

- 普通写作前后项目文件树不变。
- 普通写作前后 `%USERPROFILE%\.meecho\` 不变。
- 明确管理动作才尝试写入。
- 用户拒绝权限后没有部分文件。
- 返回内容在聊天中，不创建草稿文件。

**完成标准：** 所有文件读写边界正确；不对生成文字作风格评价。

### 任务 7：运行客观功能测试

**目的：** 在接触私人文章前，证明产品的安装、路径、权限和零写入边界正确。

**输入：** 只使用合成语料和合成 profile。

**测试清单：**

- [ ] Plugin 可以安装、更新和卸载。
- [ ] Plugin 中只有一个显式 `meecho` Skill。
- [ ] 未显式调用时不读取 profile。
- [ ] 显式 `build` 可以通过 Codex 宿主读取合成 `.docx`，并识别预期标题、
  首段、中间段和末段的客观标记。
- [ ] `.doc`、`.docm`、损坏、加密和伪装扩展名被拒绝；拒绝过程不提示安装
  Word、LibreOffice、Python、Java 或其他转换器。

每项结果都必须有本地日志。日志只记录路径、文件清单、哈希、退出状态和错误，不评价生成文字。

### 任务 10：Codex 出题，用户完成最终盲评

**这是整个 V1 的最后一个任务，也是唯一评价风格模仿是否有效的任务。**

#### 1. Codex 出六道题

题目只在档案完成后编写，覆盖：

1. 无参考的新场景写作。
2. 把一段中性文字改成目标声音。
3. 与目标语料题材完全不同的跨题材写作。
4. 有明显情绪但禁止直接说明情绪的场景。
5. 对话较多、容易丢失叙述声音的场景。
6. 如果档案中存在第二种稳定声音，则指定该声音；否则测试较长篇幅中的声音稳定性。

题目不得复述封存作品情节，不得包含私人原文句子，也不得针对已经知道的模型弱点故意偏袒 Meecho。

#### 2. 每题生成两份匿名候选

- 一份使用普通模型，不调用 Meecho、不读取私人档案。
- 一份显式调用 `$meecho:meecho` 并读取用户选定的目标声音档案。
- 两份使用同一模型、同一 reasoning、同一题目；去除空白后的长度差不得超过较短一份的 `15%`。
- 每题独立随机决定哪份显示为 A、哪份显示为 B。
- 映射保存在 `%USERPROFILE%\.meecho\evaluations\<evaluation-id>\mapping.json`；写入前请求用户批准。
- 用户完成选择前不得显示映射。

#### 3. 在聊天中让用户选择

每题只提供四个选项：

- `A 更像`
- `B 更像`
- `没有明显区别`
- `两份都不像`

用户可以补充一句原因，但不要求数字评分。

Codex 只记录用户原话，不得自行改写为分数，不得把“不确定”算成 Meecho 成功。

#### 4. 用户完成后才揭盲

揭盲结果只展示：

```markdown
| 题目 | 用户选择 | A 实际来源 | B 实际来源 | 用户原话 |
|---|---|---|---|---|
```

不生成总分、相似度百分比或 AI 解释。是否“已经明显不同”由用户本人作一句最终判断。

#### 5. 用户不满意时继续改

如果用户选择“没有明显区别”或“两份都不像”，Codex 根据用户的具体反馈修改档案规则或例句，然后使用六道全新题重新盲评。

不得重复旧题调提示词，也不得由 Codex宣布“已经足够好”。循环结束的唯一条件是用户明确表示接受当前效果，或用户决定停止。

**完成标准：**

- 六道题由 Codex 创建。
- 十二份候选在用户看来是匿名的。
- 映射在用户选择完成后才揭示。
- 用户的选择和原话被准确记录。
- 最终结论来自用户本人，而不是 Codex。
