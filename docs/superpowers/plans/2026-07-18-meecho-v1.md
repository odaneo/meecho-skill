# Meecho V1 全局声音档案 Plugin 实施计划

> **供执行计划的智能体使用：** 必须使用 `superpowers:subagent-driven-development`（推荐）或 `superpowers:executing-plans` 逐任务实施，并使用复选框（`- [ ]`）跟踪进度。

**目标：** 构建一个可通过 GitHub marketplace 安装的 Meecho Plugin；Plugin 内只包含一个显式调用的 `meecho` Skill，使用户可以从本地旧作建立一份本机全局私人声音档案，并在任意 Codex 项目中调用它完成写作或润色，日常结果只返回到聊天中。

**架构：** 最终产品是一个无自定义运行时的 Codex Plugin，Plugin 内含一个名为 `meecho` 的纯说明型 Skill。通用工作流随 Plugin 安装；私人高中声音档案独立保存在当前操作系统用户的 `~/.meecho/`，不写入 Plugin 缓存、项目目录、全局 `AGENTS.md` 或另一个用户 Skill。普通写作与润色只读取档案并返回一份聊天正文；只有建立档案、更新档案、明确记住偏好、导出和删除等管理动作可以写本地文件。

**技术栈：** Codex Plugin、Codex Skill、Markdown、YAML、JSON、JSONL、Git、GitHub Actions；源码开发阶段使用官方 `plugin-creator`、`skill-creator`、官方校验器、Codex fresh agents、PowerShell、开发 Python／`python-docx` 和可选 Word／LibreOffice 转换。安装后的 Plugin 不需要 Python、Node.js、数据库、API Key、MCP Server、Hook 或后台服务。

## 全局约束

- 最终产品必须准确表述为：**一个 Meecho Plugin，内部包含一个 `meecho` Skill**。
- 用户只安装 Plugin；不得要求用户单独安装、生成或手工复制 Skill。
- Skill 的 `agents/openai.yaml` 必须设置 `policy.allow_implicit_invocation: false`。
- Plugin 内 Skill 的规范文本调用名是 `$meecho:meecho`（`Plugin 名:Skill 名`）；桌面端也可通过 `@` 选择 Meecho 内的 `meecho` Skill。裸 `$meecho` 是独立本地 Skill 的写法，本项目不安装这种第二份 Skill，因此不得承诺它生效。
- 普通“使用 Meecho”“写作”或“润色”等自然语言请求不得隐式加载声音档案；必须出现规范调用 token，或由客户端的 Skill 选择器显式插入等价引用。
- 这不是 Meecho 自定的命名偏好：当前官方 [Build plugins](https://learn.chatgpt.com/docs/build-plugins) 规范把 Plugin `name` 用作组件命名空间，官方 bundled Skill 示例也使用 `$plugin-name:skill-name`；[Build skills](https://learn.chatgpt.com/docs/build-skills) 则说明 `allow_implicit_invocation: false` 后仍可显式调用。
- 全局私人数据根目录固定为当前用户的 `~/.meecho/`；Windows 对应 `%USERPROFILE%\.meecho\`。
- 私人档案不得写入 `~/.codex/plugins/cache/`、`~/.codex/AGENTS.md`、`$HOME/.agents/skills`、当前项目或 GitHub 仓库。
- 日常 `write`／`revise` 只读全局档案，默认返回一份最终聊天正文，不写 `drafts/`、`sessions/`、候选文件、故事状态或当前项目文件。
- 只有用户明确请求 `build`、`update`、`remember`、`export` 或 `delete` 时，Skill 才可以执行任何本地文件写入或删除；普通写作、润色、状态查看和评估本身全部只读。
- 首次建立、更新、迁移、备份或删除全局档案可能触发工作区外写入审批；Skill 必须接受审批结果，不得修改 Codex 全局权限或 writable roots 绕过审批。
- 日常读取被环境策略拒绝时必须停止并说明具体路径，不得退化为泛化仿写或自动加载公开示例。
- Plugin 更新、重装或卸载不得删除 `~/.meecho/`。
- V1 档案 schema 固定为 `1`；遇到更高或更旧版本都必须停止。V1 不实现迁移，只能说明未来迁移必须先备份并另获明确授权，禁止静默破坏性迁移。
- 原始高中作品和成年博客保持原位、保持原文，不复制进 Plugin 或 GitHub。
- 全局档案可以保存少量经选择的私人例句，但不得保存完整原文；例句进入当前模型上下文的事实必须向用户说明。
- 成年博客只作时期对照，不得自动定义为负样本或“错误风格”。
- 必须按完整作品族划分开发语料和封存语料；封存作品不得参与档案编译、例句选择或提示优化。
- 每条高可信风格规则至少需要两个独立作品族的证据，并记录反例或适用边界。
- 不训练、微调、继续预训练、蒸馏或修改任何模型权重。
- 本计划保留的“蒸馏自己文字”只是产品层比喻：实际技术是把本地语料编译成可审阅的证据型 Markdown／JSON 档案，并在每次请求中做任务相关的动态例句选择与上下文学习；它不是模型蒸馏。
- 不使用 LoRA、SFT、DPO、RLHF、prompt tuning、soft prompt、activation steering、logit steering、作者分类器或个性化评分参数拟合。
- Plugin 内不得存在 `scripts/`、Python、JavaScript、数据库、向量库、模型文件、依赖清单、Hook、MCP 配置或 App 配置。
- Python 只允许用于开发脚手架、官方校验、Word 私人导入、合成 fixture 和 CI，不是 Plugin 安装者的运行依赖。
- V1 正式支持 Codex 桌面端和 Codex CLI；不得声称 Plugin 可在 IDE Extension 中安装使用。
- 用户本人匿名盲选是声音相似性的主要评价；自动检查只作辅助。
- V1 面向约 12 篇高中作品、若干成年博客和场景级中文输出，不承诺数学意义上的“无限接近”或长篇小说全局一致性。
- Skill 遇到非关键缺失信息时采用保守默认值并一次性批量呈现假设，不得连续逐项盘问。
- 真实私人语料只在任务 9 接入；任务 1–8 只用合成文本和合成 Word fixture，开发者在此之前不需要提供高中作品。
- 用户现有 `.doc`／`.docx` 原件保持只读。任务 8 创建的仓库外开发导入器可把它们转换为 UTF-8 中间文本供任务 9 使用；该导入器位于 `tools/dev/`，不进入 Plugin，也不成为安装者运行依赖。
- 本地调试分两级：开发者当前环境中的快速校验／重装／合成冒烟只用于缩短反馈环；发布门槛是在当前 Windows 用户下启动的本地 Meecho 评测测试舱中完成配对隔离测试，快捷模式不得冒充安全验收。
- 评测测试舱必须同时隔离 `CODEX_HOME`、测试用 `USERPROFILE`／`HOME`、case 工作区和 `~/.meecho`，并使用最小文件权限配置、`codex exec --ephemeral`、干净临时 Git 仓库和逐步日志；不得再要求、检测或假设存在专用 Windows 用户。
- 正式测试舱最低要求 Codex CLI `0.145.0`，但版本号只是第一道门槛；preflight 还必须动态证明本计划使用的 `codex exec` 参数、permission profile、`CODEX_SQLITE_HOME` 和配置字段都被当前 CLI 接受。能力探针或实际拒绝 canary 任一失败，都必须标记 `BLOCKED_NOT_RUN`，不得仅凭版本号放行。版本依据见官方 [Codex changelog](https://learn.chatgpt.com/docs/changelog#codex-2026-07-23-app)。
- `--ephemeral` 只用于禁止本次 exec 持久化 rollout，不被表述为完整隔离。完整隔离还依赖独立 `CODEX_HOME`、每 scenario 独立 `CODEX_SQLITE_HOME`、虚拟 home、白名单环境变量、permission profile 和实际 read／allow／deny canary。
- 正式 Meecho-off／Meecho-on 证据必须由同一条配对命令背靠背产生 fresh control 与 treatment；不得把数天前的历史 RED run 与当前 treatment 拼成改进结论。

## 一、统一术语与产品边界

### 1. Meecho Plugin

用户从 Plugins Directory 或 GitHub marketplace 安装的唯一产品。它负责：

- 被安装、启用、停用、更新和卸载。
- 向 Codex 提供一个 `meecho` Skill。
- 携带通用工作流、数据契约和空白模板。

Plugin 本身不包含用户原文或用户档案。

### 2. `meecho` Skill

Plugin 内唯一的行为核心，目录为 `plugins/meecho/skills/meecho/`。它负责：

- 在用户显式调用 `$meecho:meecho` 后选择工作流。
- 建立、读取、更新、检查、导出或删除全局声音档案。
- 根据档案进行写作和润色。
- 执行隐私、审批、输出和评估边界。

它不是用户单独安装的第二个产品，也不会生成另一个私人 Skill。

### 3. 全局私人声音档案

由 `$meecho:meecho` 在用户明确请求后创建的数据，位于：

```text
~/.meecho/
├── config.json
├── profiles/
│   └── high-school/
│       ├── manifest.json
│       ├── style-profile.md
│       ├── attention-lens.md
│       ├── voices.md
│       ├── exemplars.jsonl
│       └── preferences.md
├── backups/
│   └── high-school/
```

“全局”只表示当前电脑、当前操作系统用户的不同 Codex 项目可以读取同一档案；V1 不提供跨电脑、跨账号或云端同步。

### 4. 聊天输出

普通 `$meecho:meecho` 写作或润色的交付物就是模型在当前对话中返回的文字。默认不保存、不修改项目文件、不写偏好、不创建会话记录。

### B. Plugin 安装包

安装缓存只能包含 `plugins/meecho/` 的发布内容：

- `.codex-plugin/plugin.json`
- `skills/meecho/SKILL.md`
- `skills/meecho/agents/openai.yaml`
- Skill references
- Skill templates

安装包明确不得包含：

- 用户语料或用户档案。
- `examples/odane-highschool/`。
- `evals/`、`docs/` 或 `.github/`。
- `tools/` 及其 Word 导入器、本地调试脚本和测试。
- `scripts/`、`*.py`、`*.js`、`package.json`、`requirements.txt`。
- `.mcp.json`、`.app.json`、hooks、数据库、模型或 embedding。

### C. 用户全局私人数据

`~/.meecho/` 由用户拥有，不属于 Plugin 安装包。Plugin 升级、重装和卸载都不得触碰它。

V1 保存：

- 当前激活的档案 ID。
- 证据型风格档案。
- 注意力镜头与声音差异。
- 少量代表例句。
- 用户明确要求记住的现代偏好。
- 更新或 schema 迁移前的备份。

V1 不保存：

- 完整高中原文或完整成年博客。
- 日常生成和润色结果。
- 常规 session 日志。
- 当前项目草稿。
- 故事状态或长篇小说状态机。
- 自动收集的聊天记录。
- 自动保存的评估候选、盲选或评分记录；显式评估先在聊天中返回，只有后续明确 `export` 才可落盘到用户指定位置。

### D. 可选公开示例

`examples/odane-highschool/` 只用于 GitHub 展示和复现实验说明。它：

- 不进入 Plugin 安装包。
- 不自动参与任何用户的生成。
- 不作为用户没有档案时的 fallback。
- 不包含原始作品全文、未经许可的原文摘录、私人路径、哈希、偏好原件或封存数据。

## 三、普通用户流程

### 1. 安装一次

GitHub 测试版：

1. 用户把 README 中经过验证的 GitHub 仓库地址传给 `codex plugin marketplace add`，不得手工编辑 `config.toml`。
2. 运行 `codex plugin marketplace list`，确认出现名为 `meecho` 的 marketplace 及其解析路径。
3. 重启 Codex 桌面端；在 **Plugins** 中选择 Meecho marketplace 并安装 Meecho。CLI 用户进入 `/plugins`，切换到 Meecho marketplace 后安装。
4. 新建任务／session，使 Plugin 内的 Skill 进入新上下文。

正式进入 Plugins Directory 后，用户只需搜索 Meecho 并点击安装。

### 2. 建立一次全局档案

用户在 Codex 中打开包含本地高中作品的文件夹，显式输入：

```text
$meecho:meecho 使用当前文件夹中的高中作品建立我的全局高中声音档案；成年博客只作时期对照。
```

Skill 读取原文但不修改或复制原文，经过批量审核后写入 `~/.meecho/profiles/high-school/`。工作区外写入由 Codex 正常审批。

### 3. 在任何项目中使用

用户打开任意项目，输入：

```text
$meecho:meecho 用我的高中声音润色下面这段，只输出润色后的正文：……
```

Skill 读取同一份全局档案，返回一份聊天正文，不修改当前项目。

### 4. 明确更新

只有下列请求允许改变全局档案：

```text
$meecho:meecho 用当前文件夹中的新增旧作更新 high-school 档案。
$meecho:meecho 记住这个当前偏好：不要把含混的结尾改成明确总结。
$meecho:meecho 导出 high-school 档案的本地备份。
$meecho:meecho 删除 high-school 档案。
```

更新前必须备份。删除必须展示准确路径并再次确认。普通写作反馈不会自动写入偏好。

## 四、开发过程需要的工具

| 工具 | 开发用途 | 是否进入最终 Plugin | 安装者是否需要 |
|---|---|---:|---:|
| Codex 桌面端或 CLI | 创建、安装和前向测试 Plugin／Skill | 否 | 是，作为宿主 |
| Git | 版本控制与 diff 审查 | 否 | 否 |
| GitHub | 仓库托管和 marketplace 分发 | 否 | 仅安装时访问 |
| `plugin-creator` | 生成和校验 Plugin／marketplace | 否 | 否 |
| `skill-creator` | 初始化、生成 UI metadata、校验 Skill | 否 | 否 |
| Codex fresh agents | RED 基线、行为前向测试、隔离复核 | 否 | 否 |
| 独立 `CODEX_HOME`＋permission profile＋`codex exec --ephemeral` | 在同一 Windows 用户下建立 Meecho-off／Meecho-on 本地配对测试舱 | 否 | 否 |
| PowerShell 7.4+／`rg` | 运行测试舱、使用 `ProcessStartInfo.ArgumentList`／环境清洗、检查路径、禁止文件、无写入和敏感信息 | 否 | 否 |
| PowerShell `meecho-dev.ps1` | 一条命令执行环境诊断、Word 导入、校验、重装和合成冒烟 | 否 | 否 |
| Codex bundled Python＋`python-docx` | 开发期抽取 `.docx`、生成合成 fixture、运行官方校验器和 CI JSON 校验 | 否 | 否 |
| Microsoft Word COM | 当前 Windows 开发机把旧 `.doc` 的只读副本转换成临时 `.docx`；本机已检测到 Word | 否 | 否 |
| LibreOffice／`soffice` | 没有 Word 时可选的开发期 `.doc` 转换后备；不得成为 Plugin 依赖 | 否 | 否 |
| GitHub Actions | 自动执行结构和边界检查 | 否 | 否 |

测试舱 harness 明确要求 PowerShell 7.4+，不支持 Windows PowerShell 5.1；`doctor` 必须在执行任何 run 前报告解析到的 `pwsh` 版本。当前开发机已验证 bundled Python 含 `python-docx`，并检测到 `C:\Program Files\Microsoft Office\Root\Office16\WINWORD.EXE`；未检测到 PATH 中的 `soffice`。最终 Plugin 的运行依赖仍只有 Codex 及其本地文件读取能力，PowerShell 和 Python 都只是源码开发工具。


三个 permission mode 的语义固定为：

- `PermissionMode=allow`：通过 `-c default_permissions="meecho-capsule-allow"` 选中 allow profile，并把本 scenario `user-home` 作为唯一额外 workspace root 传给 `--add-dir`，表示审批已经允许后的可写状态。
- `PermissionMode=read`：通过 `-c default_permissions="meecho-capsule-read"` 选中 read profile，不传 `--add-dir user-home`；借助虚拟 `HOME` 只把本 scenario 的 `~/.meecho` 重新开放为只读，普通润色、跨项目读取和 `status` 使用此模式。
- `PermissionMode=deny`：通过 `-c default_permissions="meecho-capsule-deny"` 选中 deny profile，不传 `--add-dir user-home`；它同样允许 Skill 读取本 scenario 的现有 `.meecho` 以理解目标，但任何管理写入都被拒绝，表示审批被拒绝后的状态。

read 与 deny 当前拥有相同的底层文件权限，区别是被测请求与预期：read scenario 只发只读请求并验证零写入；deny scenario 发管理写请求并验证失败且无部分结果。两者保留独立 profile 名和独立路径，以免把“正常只读成功”与“写入被拒绝”混成同一种证据。

三种模式都把当前 scenario 工作区设为主 workspace；真实用户主目录、真实 `~/.meecho`、真实 Plugin cache 和其他 case／scenario 均不进入有效 workspace roots。自动化 `codex exec` 一律使用 `-c approval_policy="never"`，所以它只验证“只读保持零写入”“允许后成功”和“拒绝后安全停止”三个确定状态，**不声称验证了交互式审批弹窗本身**。不得同时传入会覆盖 permission profile 的 `--sandbox`，也不得使用会跳过测试舱配置的 `--ignore-user-config`。control 与 treatment 对同一 case／scenario 必须使用相同 `PermissionMode`。

官方文档依据：

- [`CODEX_HOME` 控制配置、认证、日志、会话和 Skills](https://learn.chatgpt.com/docs/config-file/environment-variables#core-locations)。
- [`codex exec` 支持 `--ephemeral`、`--ignore-rules`、JSON 事件和最终消息文件](https://learn.chatgpt.com/docs/developer-commands#codex-exec)。
- [Codex permission profile 可以只开放 `:minimal` 与 workspace roots](https://learn.chatgpt.com/docs/permissions#filesystem-permissions)。
- [Codex 配置参考定义了 file auth store、reasoning、personality、permission profile、shell 环境和 SQLite state 等字段](https://learn.chatgpt.com/docs/config-file/config-reference#configtoml)。

初始化器必须在运行任何 case 前验证：

1. 子进程 `CODEX_HOME` 与真实 `~/.codex` 不同，并且 control home 中没有 Meecho Plugin、Meecho Skill 或其引用。
2. 子进程 `USERPROFILE` 和 `HOME` 都解析到当前 scenario 的 `user-home`，不等于真实用户主目录。
3. `ScenarioRoot` 固定为 `<RunRoot>\<Mode>\<CaseId>\<ScenarioId>\`；`CODEX_SQLITE_HOME`、`USERPROFILE`／`HOME`、`TEMP`／`TMP`、`LOCALAPPDATA`／`APPDATA` 和 workspace 全部位于这个 scenario root；`StepLogRoot` 也必须含同一 mode／case／scenario 层。preflight 对整个 pair 建立路径集合并断言每个组合互不相同，禁止 read／allow／deny 复用任何可变目录或日志目录。
4. 测试舱及 scenario 路径规范化后仍位于 `%LOCALAPPDATA%\MeechoDev\eval\`，中间目录不存在 symlink／junction／reparse-point 逃逸；每个 scenario 工作区位于仓库外、是独立临时 Git 仓库，且只包含该 scenario 声明的合成文件。
5. read canary 在 `PermissionMode=read` 时能读取预置的虚拟 `~/.meecho` 文件，但模型生成的写入失败；allow canary 在 `PermissionMode=allow` 时真实写入并清理成功；deny canary 在 `PermissionMode=deny` 时能读取目标 manifest，但模型生成的管理写入失败且没有部分文件。只解析 TOML 或观察参数不算通过。
6. 仓库外另建的拒绝 canary、真实 `~/.meecho` 和其他 case／scenario 均不可由模型生成的命令读取。
7. `ProcessStartInfo.Environment.Clear()` 后只注入白名单：`SystemRoot`、`WINDIR`、`COMSPEC`、`PATHEXT`、经最小化的 `PATH`、`ProgramData`、`ProgramFiles`、`ProgramFiles(x86)`、`CommonProgramFiles`、`CommonProgramFiles(x86)`、`USERNAME`、`USERDOMAIN`，以及显式重写到 case 目录的 `TEMP`、`TMP`、`LOCALAPPDATA`、`APPDATA`、`USERPROFILE`、`HOME`、`CODEX_HOME`、`CODEX_SQLITE_HOME`。不得传递任何名称匹配 `KEY`／`SECRET`／`TOKEN` 或 `OPENAI_*` 的变量；manifest 只记录生效的变量名，不记录值。
8. harness 在整个 run 前后记录真实 `~/.meecho` 的目录与 SHA-256 inventory，结果必须完全相同；该 inventory 不包含文件正文。
9. `codex` 版本、明确传入的模型、固定 reasoning、实际复制到该 `CODEX_HOME/config.toml` 的 SHA-256、完整 CLI 参数（敏感值脱敏）、permission mode、环境变量名、case 输入哈希和 canary 结果写入 manifest。不得把仓库模板哈希冒充实际生效配置哈希。
10. capability probe 证明当前 CLI 至少为 `0.145.0`，并实际接受 `--ephemeral`、`--ignore-rules`、`--json`、`--model`、`--output-last-message`、`-c default_permissions=...`、`CODEX_SQLITE_HOME` 和模板中的字段。
11. 对应 `CODEX_HOME` 已认证。未认证时返回 `AUTH_REQUIRED`，只允许通过初始化器的 `-Login` 子进程完成登录；`cli_auth_credentials_store="file"` 保证认证留在隔离 `CODEX_HOME`，不得复制、哈希、打印或记录真实／测试 `auth.json` 的内容。

认证缺失时先写 manifest 和逐步日志，再以 `AUTH_REQUIRED` 停止；其余任一检查失败都以 `BLOCKED_NOT_RUN` 停止。清洗环境后若认证 CLI 无法联网，也以 `BLOCKED_NOT_RUN` 停止，绝不恢复父进程中的代理凭据或 token。没有专用 Windows 用户不再是阻塞条件。

- 源码开发和任务 9 可使用 `tools/dev/meecho-dev.ps1 import-word`：`.docx` 由开发期 `python-docx` 抽取；`.doc` 优先由本机 Microsoft Word COM 在私人 staging 中生成临时 `.docx`，无 Word 时才尝试 LibreOffice。两者都不是 Plugin 运行依赖。
- Word 导入器只能规范化技术性换行并保留段落边界、标点、错字、重复、制表符和对话节奏；不得自动润色、纠错、全半角转换或标点统一。发现修订、批注、文本框、嵌入对象或无法稳定抽取的结构时，对整批生成 warning 清单，不逐文件盘问，也不得静默丢弃。
- PDF 和 OCR 仍不在 V1 保证范围内。
- 原件不改错字、不统一标点、不润色、不移动。
- 为每篇作品分配 `work_id` 和 `family_id`，不把绝对路径写入全局档案。
- 未知年份、体裁或模仿来源写 `unknown`，不得猜测。
- 成年博客单独标记为 `adult-contrast`。
- 封存 20% 左右的完整作品族，编译阶段不得读取其正文。

- [ ] **步骤 2：定义三层证据提取**

`profile-compilation.md` 固定三层：

1. 表层文体：句长、段落节奏、标点、对话、重复、虚词和语序。
2. 叙事习惯：视角、进入场景方式、信息延迟、人物动作、转场和结尾。
3. 过去自我镜头：注意什么、忽略什么、如何比喻、如何面对权威、含混和情绪。

每条高可信主张必须包含：主张、两个以上作品族证据、反例、适用场景、voice、置信度和禁止过度推广的边界。

不得假设约 12 篇作品能一次全部进入上下文。建档必须按完整作品族分批：逐篇／逐族读取 → 生成只含抽象观察、证据计数、反例和短例句的 evidence card → 跨作品族综合。用户已显式请求 `build` 且批准工作区外写入后，临时 evidence card 才可写到本次 staging 的 `_working/` 子目录；不得写完整原文、绝对路径或封存正文。最终 live profile 完整性检查必须断言 `_working/` 已删除，Plugin 与正式 `~/.meecho/profiles/PROFILE_ID/` 都不保留工作缓存。

- [ ] **步骤 5：定义建档审核和写入事务**

`build`／`update` 开始时，先说明会创建事务 staging，并接受工作区外写入审批；该审批只允许生成可丢弃的 evidence card，不等于批准替换 live profile。分析完成后，Skill 必须在聊天中一次性批量展示：

- 主要风格主张及证据数量。
- 反例和不确定项。
- 成年对照结论。
- 候选声音。
- 代表例句范围。

用户审阅并明确批准后才把 staging 提升为 live profile；拒绝时删除本次 staging，旧档案不变。采用可恢复的 staged swap，不假设 Windows 可以把目录重命名到一个已存在的目标。每次事务生成 UTC ID（如 `20260718T153045Z`），路径和顺序固定为：

1. 初始写入审批通过后创建 `profiles/.high-school.staging-YYYYMMDDTHHMMSSZ/_working/`，不碰 live profile；实际事务中的时间串必须是当次 UTC 时间。最终审阅批准后，在同一 staging 生成正式档案文件、删除 `_working/`，再写 `config.staging-YYYYMMDDTHHMMSSZ.json`。
2. 完整性检查 staging、`manifest.json`、例句 JSONL、staging config，并断言 `_working/` 不存在；若发现同一 profile 遗留的 staging／rollback，停止并进入恢复流程，不覆盖它。
3. 若是更新，先把 live profile 复制到 `backups/high-school/YYYYMMDDTHHMMSSZ/`，再把 `profiles/high-school/` 重命名为 `profiles/.high-school.rollback-YYYYMMDDTHHMMSSZ/`；若是首次建立，跳过这一步。
4. 把 staging 重命名为 `profiles/high-school/`，再以同目录临时文件替换 `config.json`；最后重新读取 live profile 与配置做一致性检查。
5. 全部成功后才删除 rollback 和临时 config。任一步失败时，把新 live 移到失败隔离名、把 rollback 恢复为 `profiles/high-school/`、保留旧 `config.json`，并报告人工可审阅的残留路径。

审批拒绝或 staging 检查失败时清理本次新建的 staging，并保留旧档案与旧配置不变。协议只要求文件系统级可恢复事务，不宣称跨文件的数据库式原子性。

```markdown
# Meecho

Operate only after explicit `$meecho:meecho` invocation or the client's equivalent explicit Skill selection. Keep model weights frozen. Never create a second user Skill.

Read `references/storage-and-privacy.md`. Use `%USERPROFILE%\.meecho` on Windows and `$HOME/.meecho` elsewhere. Never use a project folder, Plugin cache, global `AGENTS.md`, a user Skill, or a prompt-supplied override as profile storage.
```

```powershell
function Get-TreeInventory([string] $root) {
  if (-not (Test-Path -LiteralPath $root)) { return 'MISSING' }
  Get-ChildItem -LiteralPath $root -Force -Recurse |
    Where-Object { $_.FullName -notmatch '[\\/]\.git([\\/]|$)' } |
    Sort-Object FullName |
    ForEach-Object {
      $relative = [IO.Path]::GetRelativePath($root, $_.FullName)
      if ($_.PSIsContainer) {
        "D`t$relative"
      } else {
        $hash = (Get-FileHash -LiteralPath $_.FullName -Algorithm SHA256).Hash
        "F`t$relative`t$hash"
      }
    }
}
```

- [ ] 每条高可信规则至少两个作品族并记录反例。
- [ ] 成年博客不被自动当作负样本。
- [ ] 封存作品不参与档案编译或例句选择。
- [ ] 普通生成动态选择相关规则和 4–6 个跨作品族短例句。
- [ ] 复制检查能力边界公开，不声称数学证明。
- [ ] Meecho-off RED 基线真实失败过；正式改进结论来自同一 pair run 中背靠背执行的 fresh control＋treatment，并证明 Codex binary、模型、reasoning、配置、permission mode、approval policy、环境变量名、case 和 rubric 哈希一致；历史 baseline 不参与发布比较。
- [ ] 真实本人盲测报告 `B0`、`B1`、`B2`、`M1` 的分项结果。

### 公开示例

- [ ] 公开示例经 publication manifest 白名单和所有者逐文件批准。
- [ ] 不含原文、私人例句、路径、哈希、偏好、封存证据或私人评估明细。
- [ ] 不进入 Plugin 安装包，不自动参与生成，不是无档案 fallback。
- [ ] provenance 说明派生方式、模型生成部分、评估样本量和限制。
